Small engineering decisions — optional

The aim is to reason about requirements and tests, not memorise complex software architectures or university design patterns.

Three worked challenges

1. A requirement without a test

Requirement: “The monitor should work reliably.” Replace this vague sentence with two examples having an input and expected output.

Suggested solution

Given 17 °C, show HEAT ON. Given a missing sensor reading, show CHECK SENSOR. These examples can be checked with two assert statements.

2. A component that does too much

A single Sensor class reads temperature, writes a report, sends emails and manages a dashboard. Which responsibilities could be separated? Explain using one dependency arrow.

Suggested solution

Keep Sensor responsible for reading only. A Controller decides messages; a Display shows them. If you later change how reports are shown, the sensor need not change.

3. Review an AI-assisted patch

An assistant suggests replacing the missing-data check with if not value: .... Is this always equivalent to if value is None: ...?

Solution

No. not value is true when the valid measured value is 0, whereas value is None is true only for the missing-value marker. Even if our classroom uses temperatures 10–28, a robust program should represent the distinction correctly.

Teacher background

UAIC SE02, SE03, SE06 and SE11 cover requirements, class diagrams and software quality. Only the concrete ideas above are expected at school level. Do not require full UML notation, SOLID, design-pattern catalogues, professional CI/CD or Scrum ceremonies.
