Git, GitHub and AI-assisted code editing

An introductory version-control guide before Module III.

1. Why keep versions?

You fix a bug, but your next edit breaks the program. A version history lets you identify the change and return to a working state.

The smallest cycle is edit → inspect → test → save a version.

2. Try a miniature Git workflow

Use the controls to modify a simulated project and record two commits. It is a learning activity, not a real Git repository.

Working tree has uncommitted text.

    3. The equivalent real Git commands

    git status
git add main.py
git commit -m "Add missing-input check"
git log --oneline

    A repository tracks project files. A commit records a state. A branch is a separate line of changes. A pull request proposes merging reviewed work.

    Using github.dev or vscode.dev for reading/editing source may be possible without an account; publishing to GitHub requires an account and appropriate permissions. That remains optional for students.

    4. Using an AI coding assistant responsibly

    Give the assistant a small goal and the relevant code, not an entire secret project.

    Example instruction:

    “Explain this Python function to a beginner. Suggest one small improvement, show exactly which lines change, and give a test input that would fail before the change.”

    1. Read the proposed change before applying it.
    2. Run the example and one new test yourself.
    3. Save a new version only if the result is understood and correct.
    4. Never paste classmates’ personal data, passwords, keys or private records into an AI tool.
