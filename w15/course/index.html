Week 15 · Course

FiiCode IV: Reproduce, Present and Hand Off

Teacher Guide One 60-minute session; core + optional Research

Learning outcome

Run a single final test with frozen settings; demonstrate and communicate reproducibility.

Teaching sequence

0–13 freeze configuration; 13–25 reveal hold-out results; 25–45 demonstrate application and tests; 45–55 peer review; 55–60 hand-off.

Core: reproducible observations, one experiment and an explanation in ordinary language. Research (3p): additional mathematics, model investigation or application engineering. All features and labels in this project are synthetic; do not infer student traits or real room conditions.

Independent preparation project: these are deliberately simulated examples for practising data analysis and software engineering. They are not official FiiCode rules, datasets, judging criteria or submissions.

15.1. Present a complete project, not a screenshot

At the end of four linked sessions there should be one reproducible system: a stated problem, an auditable dataset, a baseline, a working browser application, a tested Python implementation, comparisons on validation data, a frozen model, and a final evaluation.

The goal is not simply to show a large percentage. A reviewer should be able to open the repository, run python evaluate.py, reproduce the reported output and describe exactly what the application does. An application with no reproducible code or measured results is not ready for hand-off.

15.2. Evaluate once on the final 45 examples

After selecting k=1 exclusively from validation, evaluate the frozen implementation on the 45 reserved simulated test examples. The reproducible result is 38/45 = 84.4%. The final confusion matrix is:

There are seven mistakes: three consider → good and four good → consider. The validation score was 91.1%, so even this simple classroom exercise illustrates why validation and final test performance may differ.

Report responsibly

“On 45 reserved synthetic examples from the published classroom generator, the frozen k=1 classifier correctly labelled 38 examples.” Do not claim it recommends real rooms with 84.4% reliability.

15.3. Demonstrate the product and its limitations

Ask another student to pick a room profile. Record the five input values, predicted class and contributing training examples. Compare the prediction to a stated preference. A disagreement can reveal that the generated labels are not universally correct, even when the algorithm is implemented perfectly.

A k-NN vote is an algorithmic result, not a guarantee of accessibility, comfort, educational benefit or safety. The app has no current information about actual buildings, timetable conflicts, energy use or disability accommodations. It must not silently present itself as a school service.

15.4. Test failures as carefully as success

Verify input boundaries and source integrity: Wi-Fi 1 and 5 should be valid; 0 and 6 must be rejected by the Python contract. Every row must have all five features and the label must be one of the three advertised values. The baseline and k-NN tests must use exactly the expected split sizes.

Test one edge case (e.g., no power outlets), one typical case, and an invalid input. Explain what the user sees, and provide an unambiguous way to reproduce each observation.
