Week 13 · Lab

FiiCode II: Build a Working Application

Teacher Guide One 60-minute session; core + optional Research

Learning outcome

Explain the processing pipeline; trace one k-NN prediction; connect model output to a UI.

Teaching sequence

0–12 draw the pipeline; 12–27 trace distance and votes; 27–45 use the interactive app; 45–55 test invalid inputs; 55–60 identify a limitation.

Core: reproducible observations, one experiment and an explanation in ordinary language. Research (3p): additional mathematics, model investigation or application engineering. All features and labels in this project are synthetic; do not infer student traits or real room conditions.

Contents
  • 1. Build and trace a genuine k-NN prediction
  • 2. Connect the classifier to an interface
  • 3. Test the model and its UI separately
  • Submission

Independent preparation project: these are deliberately simulated examples for practising data analysis and software engineering. They are not official FiiCode rules, datasets, judging criteria or submissions.

1. Build and trace a genuine k-NN prediction

Run the Week 13 notebook. Examine the same five feature values for the new room and one training room. The notebook computes their weighted squared distance and identifies the closest labelled examples.

  1. Run the example with 35% occupancy, 42 noise, Wi-Fi 4, outlets 1 and 60 minutes.
  2. Record the three nearest example IDs and their labels.
  3. Change only k from 3 to 1, then to 5. Record which cases change and which remain stable.
  4. Explain what it means for k-NN to “learn” from the training examples.

2. Connect the classifier to an interface

Use sliders and selectors to create two contrasting profiles. For each, write down the exact inputs, selected k, predicted class and one neighbour ID. The browser and notebook implement the same distance rule.

Loading the classroom experiment…

Try an invalid Wi-Fi value 8 in the Python input-validation task. It must raise a ValueError. The browser limits the selector to the allowed range, but the Python model must defend its own contract independently.

3. Test the model and its UI separately

For the program itself, test an expected good case, an expected avoid case and one invalid input. For the interface, check a change in the Wi-Fi or noise control and explain how the displayed neighbour ranking changes.

Deliverable: completed notebook, two input/output traces, and one deliberate invalid-input test. If using GitHub, include a commit whose message describes the functionality, not just “update”.

Research (3p): add a simple UI reset or accessibility feature, document its expected behaviour and show one test.
